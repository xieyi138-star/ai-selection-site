- 日期：2026-08-09

---

## 1. 终极之果

**赚钱。** 路径：① 企业 AI 选型咨询出现金流 → 养 ② 企业订阅 SaaS。

站本身不是收入来源，是获客漏斗 + 判优引擎的展示面。

### 完工判据（P1b 关口，非过程量）

不使用覆盖率／准确率／良率——过程量关不掉循环。

**两段串行，B 先于 A。** 原定的「盲测 5 个开发者」已于 2026-08-09 废弃：冷启动招募 5 个英文开发者对单人创始人不可执行，方案本身立不住。改为下面两段——**都不需要建站**，环节页本身就是 markdown，直接发得出去，因此止损点仍在建站之前。

#### 段 B · 文献反证（自动化，创始人零投入）

对 5 个环节各收集近 12 个月内公开的**真实选型记录**：迁移公告、工程博客「我们为什么选 X」、HN／Reddit 中实践者陈述在产环境用什么及原因。

**冲突的定义**（可判定，不靠感觉）——一条记录同时满足：
1. 明确指名本环节中某工具是其**在产选择**；且
2. 该工具被我们判为 `avoid` 或 `insufficient_data`，**或**排在一个该实践者明确拒绝过的工具之后。

> **通过：任一环节的「未解释冲突」< 3 条。**

- 「已解释」= 实践者的选择理由落在我们四轴测不到的维度（商业支持、团队既有技能、合规要求）。这是**已知盲区**，须在页面标注，不算判优错。
- 「未解释」= 实践者在生产里用，而我们的数据说它濒死／不可用。**我们和他们必有一方是错的。**

#### 段 A · 公开发帖（创始人只需发一帖）

B 通过后，将 1–2 张环节页公开发布（r/LocalLLaMA、Hacker News、X），标题明确邀请证伪：「请告诉我哪里错了」。**这不是招募，是发布**，顺带积累第一批受众。

> **通过，两条同时满足：**
> 1. 7 天内 **≥10 条实质回应**（实质 = 针对内容本身；点赞、"cool"、纯转发不计）
> 2. **0 条未被驳倒的具体事实质疑**指向任一 `primary` 结论

「未被驳倒」= 有人指出具体事实（如「X 是你的首选，但它自 v0.3 起就坏了」），我们去核，结果他是对的。

**沉默不算通过。** 实质回应 <10 = **inconclusive**，既不是通过也不是失败。

### 不通过时的动作（止损点不在第一次失败）

| 情况 | 动作 |
|---|---|
| B：某环节 ≥3 条未解释冲突 | 判优规则错 → 逐条定位是哪一轴与现实脱节 → 改规则，重跑 B |
| A：出现未被驳倒的事实质疑 | 判优规则错 → 同上 |
| A：inconclusive（回应 <10） | 换渠道／换标题**重发一次**。第二次仍 inconclusive → 此法测不出结论，升级给创始人决定 |
| **两轮返工仍不过** | ⛔ **停项目** |

## 3. 竞品实证（2026-08-09 实测）

| 竞品 | 实测结果 |
|---|---|
| gitstar-ranking.com | 总赞排名，top 10000。纯人气。 |
| EvanLi/Github-Ranking | Top100 分语言，Actions 每日更新。纯 star。 |
| GitHub 官方 Trending / Trendshift / RepoFOMO | 涨速榜。RepoFOMO 有 7/30/60 天星增长、1500+ repo。 |
| **OSSInsight `/trending/ai`** | 9 个 AI 分类（AI Agents / LLM Tools / MCP Servers / Coding Agents / RAG / Inference / Vector DB / Vibe Coding / AI Assistants）**全部显示 0 repos**，处于失修状态。 |
| **jaychempan/Agent-Leaderboard** | 5 个板块（Agent Skills / MCP Servers / Prompt Library / AI Frameworks / Auto Research），**唯一指标是 star**，Actions 每日更新。 |
| yuxiaopeng/Github-Ranking-AI | AI 主题 star 排名，中文，每日更新。 |

### 缺口结论

三层问题，难度递增：

| 层 | 问题 | 现状 |
|---|---|---|
| ① 归位 | 这个 repo 用在哪个环节 | awesome-* 列表覆盖，但人工维护、常年过期 |
| ② 收敛 | 同一用途下到底有哪 N 个 | 部分覆盖，无淘汰机制 |
| ③ **判优** | 这 N 个里哪个**真好用** | **完全空白** |

现有产品全部回答"谁火"。star 与"该不该用"统计上不相关，且是滞后、可刷的虚荣指标。

**唯一护城河 = 判优。**

## 4. 判优引擎

### 4.1 数据源可得性（已实证）

| 信号 | 可得性 | 决策 |
|---|---|---|
| GitHub 被依赖数（Used by） | ⚠️ **无官方 API**，只能爬 `/network/dependents` | 降为辅助，**不做主指标** |
| PyPI 下载量 | pypistats API 免费、180 天日粒度、限速 ~30 req/min（40 个包毫无压力） | ✅ **走 pypistats**。BigQuery 已于 2026-08-09 排除：`file_downloads` 表按日分区即达数十 GB，按日查询一个月会耗尽 1TB/月免费额度 |
| npm 下载量 | `api.npmjs.org/downloads`，免费 | ✅ |
| Docker Hub pull 数 | 官方 API `pull_count` | ✅ AI 项目常发镜像 |
| commit / release / issue 时间戳 | GitHub API，认证 5000 req/hr | ✅ |
| star 时间序列 | GitHub API `starred_at`（需特殊 Accept header），可算衰减曲线 | ✅ |

**硬缺口**：既不发包也不发镜像的纯 GitHub 项目（ComfyUI 及大量 agent 项目）**没有任何真实使用量信号**。只能靠 fork + 活性推断。

→ **设计要求：置信度必须显式标注并展示给用户。不允许在信号缺失时假装知道。** 一次装懂，公信力清零。

### 4.2 判优四维（四个独立轴，不做综合分）

单一综合分是此类产品通病：把不可通约的量加权求和，结果既无人信也无法反驳。

| 轴 | 指标 | 回答的问题 |
|---|---|---|
| **① 真的有人用吗** | 下载量／pull 的 30 天总量 + **180 天窗口内的 30d vs 前 30d 趋势** | "有人在生产里跑"，而非"有人觉得酷" |
| **② 明年还在吗** | 最近 release 间隔、90 天 commit 数、核心维护者数（bus factor） | 敢不敢押 |
| **③ 踩坑有人管吗** | issue 首响中位时间 + 90 天关闭率（两者取**最差**档） | 出事的成本 |

**每个多信号轴取「最差档」，不取平均。** 一个项目的健康度等于它最弱的那项生命体征——最近发过 release 但 90 天几乎没提交、只剩一个维护者，那是发版机器人；取平均会把这种情况藏起来。

**③ 轴的两处施工决定（2026-08-09，实测驱动）：**
- **不用「未解决 issue 增长斜率」。** 它是尺度相关的：1000 开/900 关 与 10 开/9 关 健康度相同，绝对增长却是 +100 对 +1，会系统性惩罚高流量项目。这是测量偏差不是信号；关闭率以尺度无关的方式承载了同样的信息。
- **额外采集 `issues_no_response_90d`，但暂不计入评分。** 实测 langgraph 90 天 180 个 issue、**36 个（20%）无人回复**；首响中位数只统计有回复的那些，会让「80% 提问被无视、回的那 20% 一小时内回」的仓库判成 strong。之所以现在就采：`metrics_daily` 增量累积，今天不采永远补不回来。要不要计入评分，等有了 40 个 repo 的真实分布再定。
| **④ 今天跑得通吗** | 沙箱按 README quickstart 实跑，记录成功/失败与失败原因 | **无任何竞品做——护城河** |

- 前三维：全自动，全量覆盖（40 repo）。
- 第四维：**MVP 只跑 Top 20**（成本可控，且是企业客户一眼看懂价值的东西，直接服务 ① 咨询开单）。

**Top 20 的定义**：5 个环节 × 每环节前 4 名候选 = 20。这 20 个恰好就是环节页上最显眼的那批——因此**第四维必须在 P1b 验证之前完成**（见 §9）。

### 4.4 置信度分级

置信度由信号完整度决定，**必须在页面上显式展示**：

| 级别 | 条件 |
|---|---|
| 高 | 有真实使用量信号（PyPI／npm／Docker pull）+ 活性 + issue 响应 三维齐全 |
| 中 | 缺使用量信号，但活性与 issue 响应齐全，且有可观 fork 量 |
| 低 | 仅有活性指标（纯 GitHub 项目、无包无镜像） |

低置信度条目**不得给出"首选"级别的结论**，只能陈述已知指标。

### 4.3 时间序列是硬约束

**每个 repo 一份健康档案（时间序列），不是一次性快照。**

理由：订阅（②）卖的是告警——"你在用的 3 个依赖正在死亡"。告警只能从趋势里出。建成快照库 = 将来推倒重来。

## 5. 用途地图

### 结构

**一级（我要干什么）→ 二级（要解决哪几件事）→ 三级（这件事有哪 N 个候选）**

**MVP 只做二、三级。一级留白**——一级分类需要大量真实用户访谈才做得对，现在做等于猜。

### 首批 5 个环节

选择依据：候选多、差异大、选错代价高、且都有包发布（数据信号完整）。

| 环节 | 为什么优先 |
|---|---|
| Agent 编排框架 | 候选最多、差异最大、选错重写成本最高，企业咨询需求最集中 |
| RAG / 检索 | 企业落地第一场景，方案分歧最大 |
| 向量库 | 一旦落地极难迁移，选错代价最重 |
| 推理引擎（自部署） | 直接决定成本与延迟，差异最可量化 |
| 可观测 / 评测 | 上生产必备但最常被忽略——本身就是咨询钩子 |

规模：5 环节 × 6–10 候选 ≈ **40 个 repo**。

## 6. 站的形态

### 三层页面

| 页面 | 路径 | 内容 |
|---|---|---|
| 环节页 | `/stage/agent-orchestration` | 这个环节解决什么 + **明确结论**（"要 X 选 A ／ 要 Y 选 B ／ 这三种情况别用任何一个"）+ 候选四维横向表 |
| repo 档案页 | `/repo/{owner}/{name}` | 四维时间序列图 + quickstart 实跑记录（含失败原文）+ **变化事件流**（"2026-07 起 issue 首响从 6h 恶化到 4d"） |
| 两两对比页 | `/compare/a-vs-b` | SEO 主力入口 |

### 数据模型

```
use_cases      环节地图节点
repos          身份 + 生态 + 包名映射（github ↔ pypi / npm / dockerhub）
metrics_daily  (repo_id, date, 四维原始指标)      ← 时间序列，告警的唯一基础
runs           quickstart 实跑：镜像、命令、结果、失败原因分类
verdicts       (use_case_id, repo_id, 结论, 置信度, 生成时间, 依据快照)
```

两条硬要求：
- `metrics_daily` 是快照库与订阅产品的分水岭。
- `verdicts.依据快照` 让每条结论可回溯到当时的数据；否则改规则即成黑箱，公信力守不住。

## 7. 变现

### ① 企业 AI 选型咨询（早期现金流）

- 入口：每个环节页底部固定「需要针对你们场景的选型报告？」→ 表单（技术栈／规模／约束）
- **交付形态：异步书面选型报告，不做会议。** 规避英文会议与欧美时区门槛，且可复用、可模板化。
- **飞轮**：咨询中做出的人工判断回灌成判优规则。这是唯一能让判优越来越准、竞品抄不走的循环。

### ② 企业订阅（长期主体）

AI 技术栈健康看板 + 恶化告警。P4 起做雏形。

### 明确不做

- **付费上榜 / sponsored listing**——目录站的教科书打法，但与核心资产正面冲突，且多数 repo 无商业主体，路径实质关闭。

## 9. 分期与关口

| 期 | 做什么 | 关口判据（过不了不许进下一期） |
|---|---|---|
| **P0** 采集地基 | GitHub API + pypistats + npm + Docker Hub → `metrics_daily`（40 repo，前三维） | 连续 7 天无缺口；抽查 5 个 repo 数字与官方页面一致 |
| **P1a** 沙箱实跑 | Top 20（5 环节 × 前 4）quickstart 容器实跑 + 失败原因分类 | 20 条全部有明确结果（成功／失败+原因），**不许有"未知"** |
| **P1b** 判优规则 + 结论生成 + **验证** | 四维打分、置信度分级、verdict 人审发布、5 个环节页 | **§1 完工判据（段 B 文献反证 → 段 A 公开发帖）** |
| **P2** 站上线 | 三层页面 + SEO + 咨询表单 | 首个真实咨询线索进来 |
| **P3** 订阅雏形 | 关注 repo 指标恶化 → 邮件告警 | 首个付费订阅 |

**P1a 必须先于 P1b**：第四维（跑得通吗）是唯一竞品没有的差异点，验证若不含它，测的就不是真产品。20 个容器成本可控，这个顺序不牺牲止损效果。

**P1b 被刻意置于 P2（建站，最贵一期）之前。** 判优不准 = 唯一护城河不存在 = 应当停在这里，而不是先花三个月建完站再发现。这也是 §1 把验证改成「文献反证 + 公开发帖」而不是「上线后看用量」的原因——后者要先花掉建站成本才拿到信号，止损点等于取消。

### 本 spec 对应的施工计划范围

第一版施工计划**只覆盖 P0 + P1a + P1b**。P2/P3 在 P1b 通过后另立计划——在护城河被证实之前，不为建站写一行计划。

## 10. P1b 验证执行细则

判据见 §1。本节只讲怎么执行。

### 段 B · 文献反证（自动化，创始人零投入）

**取证来源**（每个环节至少 8 条独立记录，不足 8 条则该环节判为「证据不足」，不能算通过）：

| 来源 | 检索方式 |
|---|---|
| 工程博客 | `"why we chose" <工具名>`、`"migrating from" <工具名>`、`"we switched to"` |
| HN | Algolia 搜索，近 12 个月，`points>20` 的相关讨论串及其评论 |
| Reddit | r/LocalLLaMA、r/LangChain、r/MachineLearning 中陈述在产用法的帖子 |
| 迁移公告 | 候选 repo 自身 issue／discussion 里用户说明「我们从 X 换到 Y」 |

**每条记录必须结构化落盘**（`validation/records/<stage>/<id>.yaml`）：来源 URL、日期、指名的工具、在产／试用、选择理由原文、明确拒绝过的工具。**只收「在产使用」，试玩和转发不算。**

**逐条判定**：按 §1 的两条件判断是否构成冲突；构成冲突的再判「已解释／未解释」——解释理由必须写下来，不能只打标记。

**反偏差要求**：公开文章天然偏向热门与营销强的工具，这正是我们要打破的偏差。因此**只有「未解释冲突」计入判据**——某工具在文章里被频繁提及但我们排名靠后，本身不算冲突；只有当实践者在生产里用它、而我们的数据说它濒死或不可用时，才计。

### 段 A · 公开发帖（创始人只需发一帖）

- **前置**：段 B 必须先通过。已经和文献打架的结论不该拿去公开。
- **发什么**：1–2 张环节页（选候选最多、争议最大的那个环节，通常是 agent 编排）。
- **怎么写标题**：明确邀请证伪，例：`I ranked N agent frameworks by real download volume, maintenance health, and whether their quickstart still runs today — tell me where I'm wrong`
- **必须在正文写明**：数据窗口（30 天下载量／180 天趋势）、四轴定义、置信度含义、quickstart 实跑方法。**藏方法 = 拿不到有效反驳。**
- **回应纪律**：与盲测同理——**不辩解**。有人提出事实质疑，去核，核完如实回帖说「你是对的，已改」或「我核了，数据是这样」。辩解会让后续反馈枯竭。
- **记录**：每条实质回应落盘 `validation/post-responses.yaml`：作者、链接、是否实质、是否事实质疑、核验结果。

### 判定

对照 §1 的两段通过条件。**判定必须由脚本对落盘记录计算，不靠人读印象。**
